## 要件の解釈

### スコープ

M1.1 で Discovery が広告し現在 `503` stub (M1.1 F-23) を返している `authorization_endpoint` を実体化する。`/authorize` の **認可リクエスト受付・検証 + 認可コード発行 + リダイレクト**までが範囲。トークン発行・`code_verifier` 照合・ユーザー DB・Consent 画面・クライアント登録 DB は対象外 (後続マイルストーン)。

起動前提は M1.1 と同じく K8s (HPA で複数 Pod)。Pod をまたいで認可コードフロー (`/authorize` 発行 → `/token` 交換) が成立する必要があるため、認可コードは **Pod 間で共有されるストア**に保存する (インメモリのみ不可)。reverse proxy / Ingress 経由の TLS 終端を前提とし、host header / `X-Forwarded-*` は信頼しない。

## ストア設計 (Valkey)

論点 1 で **Valkey (Redis 互換 KV)** を認可コード共有ストアに採用。PostgreSQL に認可コードテーブルは作らない (M1.2 ではマイグレーション追加なし)。フェーズ 5 で保持形式・スキーマ・操作・運用方針を確定 (Codex ベストプラクティス確認済み、`.ai-out/codex-20260531224303.md`)。

### 保持形式

**JSON 文字列を `SET` で保存** (Hash/HSET ではない)。理由: 単回使用を `GETDEL` (Redis 6.2 由来・Valkey 全バージョンで利用可、string 専用、O(1)) で atomic に取得+削除できる。Hash は `HGETDEL` (新しめのリリースを要求) または Lua が必要で互換性・複雑性が増す。フィールド単位 TTL (`HEXPIRE`) も不要 (レコード全体が同一 TTL)。

### キー

- `authz_code:<hex(SHA-256(code))>` (論点 5)。`code` は `crypto/rand` 32 バイト (256bit) を base64url した opaque 値。プレーン `code` を key にせず、ログ/ダンプ/キー一覧に平文を残さない (防御的。`code` が高エントロピー乱数のため salt 不要)

### 値スキーマ (JSON、`encoding/json`)

| フィールド              | 型                   | 必須 | 説明                                                           |
| ----------------------- | -------------------- | :--: | -------------------------------------------------------------- |
| `schema_version`        | string               |  ○   | スキーマ版数 (初版 `"1"`)。将来の移行・障害解析用 (Codex 推奨) |
| `client_id`             | string               |  ○   | 固定クライアント存在検証済みの `client_id` (F-10)              |
| `redirect_uri`          | string               |  ○   | 完全一致検証済みの `redirect_uri` (F-5 / F-10)                 |
| `code_challenge`        | string               |  ○   | PKCE challenge (F-6 / F-10)                                    |
| `code_challenge_method` | string               |  ○   | `S256` 固定 (F-6)                                              |
| `nonce`                 | string               |  ×   | 受信時のみ。M1.3 で ID Token `nonce` claim に反映 (F-8)        |
| `sub`                   | string               |  ○   | 認証済み固定ユーザー (F-10 / F-15)                             |
| `scope`                 | string               |  ○   | 発行時 scope (スペース区切り、`openid` 含む、F-3)              |
| `issued_at`             | string (RFC3339 UTC) |  ×   | 発行時刻。監査・障害解析用 (Codex 推奨)                        |

- `code` 平文・`code_verifier` は値に**入れない** (key はハッシュ、`code_verifier` は M1.3 でクライアント保持)
- `state` は**保存しない** (リダイレクトで即時返却、コードに束縛しない、F-7)

### 保存・取得操作

- **保存 (`/authorize`)**: `SET authz_code:<hash> <json> NX EX <CORE_OIDC_AUTH_CODE_TTL>` (`NX`=既存キー衝突検出/論点 5、`EX`=TTL 既定 300 秒/論点 1。RFC 6749 の 10 分上限に整合)
  - **(フェーズ 6 申し送り)** `NX` 失敗 (既存キー衝突) 時の `/authorize` 挙動を API 設計で確定する。256bit 乱数で衝突は実質発生しないが、防御的に「内部エラーとして `server_error`」または「`code` を 1 回再生成」のいずれかを明記する
- **取得+削除 (`/token`、M1.3)**: `GETDEL` で atomic 単回使用。`/token` は `not found / expired / used` を**区別せず `invalid_grant` に統一**して返す (列挙・oracle 回避、Codex 推奨)
- **TTL 失効**: `EX` でネイティブ失効。env `CORE_OIDC_AUTH_CODE_TTL` (OIDC ドメイン設定、接続系 `CORE_VALKEY_*` とは役割分離=規約接続 G) で 60〜600 秒を調整可

### 単回使用・再使用検知

- M1.2 は保存 + 単回使用可能な構造の用意まで。M1.3 が `GETDEL` で消費。
- **再使用検知 (RFC 6749 §4.1.2: コード再使用時の発行済みトークン全失効 SHOULD) と短 TTL tombstone (`authz_code_used:<hash>`) は M2.2 で追加** (Codex 推奨。M1.2 はストア interface を拡張可能にしておく)

### ストア層 interface (論点 8)

- `domain/repository` に `AuthCodeStore` interface (`Save(ctx, codeHash string, rec AuthCodeRecord, ttl time.Duration) error`。`Consume` は M1.3)、`infrastructure` に `valkeyAuthCodeStore` 実装 (valkey-go)。handler/usecase は interface に依存し M2.2 / 別実装へ差し替え可能

### Valkey 運用方針 (Codex 推奨)

- **接続セキュリティ**: prod は **TLS (`CORE_VALKEY_TLS`) + AUTH (`CORE_VALKEY_PASSWORD`) + ACL 最小権限**を必須。dev は緩和可
- **persistence**: 認可コードは短命。AOF/RDB は要件次第で、**Valkey 再起動時に未交換コードが消失することを許容する設計** (消失時クライアントは再認可フロー。dev は persistence 無効可)
- **メモリ/eviction**: `maxmemory-policy` は TTL 付きキー優先削除 (`volatile-ttl` 等)。認可コードが eviction で早期消失しないよう容量・eviction を監視 (M7.x 観測)。`/authorize` 保存失敗・`/token` 取得時の Valkey 障害は一貫して `temporarily_unavailable` (論点 11)

## DB 設計 (PostgreSQL)

M1.2 では認可コードを Valkey に保存するため、**PostgreSQL のスキーマ変更・マイグレーション追加はなし**。固定クライアント / 固定ユーザーは設定 (env / config) で定義し DB を使わない (論点 2 / 3)。クライアント登録 DB は M2.1、ユーザー DB は M3.x。
